# 开发分支与文档追踪约定（skill 留档）

> `docs-naming` skill 的补充参考。权威规范见 `../开发文档命名规范.md` §6；本文件是**可操作 checklist**。
> 一句话：**一份开发计划 = 一条独立开发分支，验证通过才合入主线，开发文档跟踪分支，README 汇总可查。**

---

## 1. 为什么（这条经验的由来）

- **改动隔离**：每份开发计划的改动只落在自己的分支，主线始终是"已验证"的稳定态，出问题可整支回滚。
- **可追溯**：从开发文档 → 分支 → 合入 commit/PR 一条链能对回；从 README 一处能查到全部计划的分支与合入状态。
- **状态可信**：文档 `已完成` = **已验证 + 已合入主线**，而非"分支上写完了"——避免"文档说完成、主线其实没有"的错位。

## 2. 命名（分支 ↔ 文档一一对应）

```
dev/<日期>-<当日序号>-<主题精简>
```

| 开发文档 | 对应分支 |
|----------|----------|
| `20260701-01-登录接口重构.md` | `dev/20260701-01-登录接口重构` |
| `20260805-01-badnode-operator并发与HA修复方案.md` | `dev/20260805-01-operator并发HA修复` |

- 主题过长可精简，但**必须能对回那份开发文档**。
- 变体前缀：修 bug 用 `fix/<主题>`，实验探索用 `exp/<主题>`；核心不变——名字对回文档。

## 3. 生命周期 checklist

- [ ] **立项**：建开发文档，`**状态**：未启动`，元信息头 `branch:` 留空。
- [ ] **动工**：从主线拉分支 `git switch -c dev/<日期>-<序号>-<主题>` → 回填文档 `branch:` → 状态改 `开发中` → README「开发文档一览」补「分支」列。
- [ ] **开发**：改动只落在该分支；进展记录按日期追加。
- [ ] **验证**：分支上跑通测试 / 实验 e2e；进展记录写验证结论（通过判据）。
- [ ] **合入**：验证通过 → 合入主线（PR / merge）→ 分支归档或删除。
- [ ] **收尾**：文档状态改 `已完成`，进展记录写「已合入主线，commit/PR: xxx」，README 该行分支标注「已合入」。

> 未通过验证不合入；文档状态停在 `开发中`，分支保留继续迭代。

## 4. 文档字段与 README 表

**元信息头**（开发文档）：

```markdown
<!--
name: <任务主题>
creator: Li Cheng
created: YYYY-MM-DD
modified: YYYY-MM-DD
branch: dev/<日期>-<序号>-<主题>      # 未建留空
related_issues: <关联问题文档>
-->
```

**README「开发文档一览」表**（每个项目）增设「分支」列，示例：

```
| 文档 | 状态 | 分支 | 一句话 |
|------|------|------|--------|
| 20260701-01-登录接口重构 | 已完成 | dev/20260701-01-登录接口重构（已合入） | 重构登录接口，拆鉴权中间件 |
| 20260702-01-推理缓存接入 | 开发中 | dev/20260702-01-推理缓存接入 | KV cache 接入推理链路 |
```

- 分支删除后（已合入）**保留分支名 + 标注「已合入」**，便于日后按分支名追溯历史改动。
- README 是**总入口**：查"哪份计划在哪条分支、验没验、合没合"只看这张表。

## 5. 边界

- 纯文档整理 / 分析（不改代码）可不建分支，`branch` 留空——本约定针对**改代码的开发计划**。
- 一份开发计划原则上一条分支；若必须拆多分支，在文档进展记录里列全部分支并各自标合入状态。

---

## 6. 问题 ↔ 修复 commit（类比 issue ↔ PR）

分支回答"在哪条线开发"，**commit id 回答"具体哪次改动"**。二者配合，文档 ↔ 代码可双向回溯。

- **问题记录文档**：修复合入后，元信息头填 `fix_commit: <短 hash>`（可多个），并在「解决方案」写明该 commit——
  **像 GitHub issue 被某个 PR 关闭**，让"这个问题哪次改动修的、改了什么"一键可查。
- **开发文档**：进展记录标注关键节点 commit / PR；合入主线时记合入 commit。
- **对应关系一览**：

  | 关系 | 锚点字段 / 位置 |
  |------|----------------|
  | 问题 → 修复它的代码 | 问题文档 `fix_commit` + 「解决方案」里的 commit id |
  | 问题 ↔ 开发任务 | 问题文档 `related_dev` ↔ 开发文档 `related_issues` |
  | 开发计划 → 分支 | 开发文档 `branch` + README「分支」列 |
  | 开发计划 → 代码变更 | 进展记录里的 commit / PR |

- checklist 补充（在 §3 生命周期基础上）：
  - [ ] 问题修复合入后：问题文档状态改 `已修复`、填 `fix_commit`、「解决方案」写 commit id 与修复时间。
  - [ ] 开发文档进展记录：关键改动标 commit；合入主线记合入 commit/PR。
